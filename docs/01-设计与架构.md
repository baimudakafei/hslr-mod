# 01 · 设计与架构

本文回答「为什么这么做」，以及每个设计取舍背后的实测依据。
想先看运行起来是什么样，请读 `02-应用模型.md`。

---

## 1. 起点：一个 Unity IL2CPP 的单机游戏

游戏是 Unity 编译的 **IL2CPP** 版：C# 被转译成 C++ 再编译成原生机器码，
只留下一个 `GameAssembly.dll` 和一份 IL2CPP 元数据。

这决定了三件事：

1. **没有可读的程序集**。不能像 Mono 那样用 dnSpy 改 IL，也不能靠反射找方法。
   要调用游戏自己的函数，只有「拿到它的地址然后直接调」一条路。
2. **模块是原生的**。所以我们的手段也是原生的：写一个 DLL 挂钩子。
3. **地址会漂移**。函数地址 = 映像基址 + RVA，而 RVA 由官方编译时决定，
   每次更新都可能变。这是本项目最大的工程难题，第 6 节专门讲。

### 为什么是「代理 DLL」而不是注入器

| 方案 | 玩家侧代价 | 稳定性 | 结论 |
|---|---|---|---|
| 注入器 / loader 进程 | 每次启动游戏前要先跑一个外部程序，杀软高概率报毒 | 差 | ✗ |
| 改游戏 exe 导入表 | 修改了游戏原文件，Steam 校验会失败 | 差 | ✗ |
| **代理系统 DLL（本项目）** | 把 DLL 放进游戏目录即可，双击游戏照常玩 | 好 | ✓ |

代理法利用 Windows 的 **DLL 搜索顺序**：exe 同目录优先于 `System32`。
所以我们在游戏目录放一个名为 `d3d11.dll` 的文件，游戏加载 D3D11 时实际加载的是它。

它必须做到两件事才能「隐身」：

1. **把 51 个 d3d11 导出原样转发给 `System32\d3d11.dll`**（画面完全不受影响）。
2. **不破坏调用约定**：转发必须是一次真实的跳转/尾调用，不能包装成普通函数
   调用再返回（会改变栈的形态）。

`shared/proxy.S` + `shared/proxy.def` 就是这两件事的实现：
`.def` 列出 51 个导出名（未做任何增删），`.S` 为每个名字生成一条
「转发到真实 d3d11 对应导出」的跳板，并在 `DllMain` 里把真实的
`System32\d3d11.dll` 加载进来、把 51 个函数指针解析好。

> 早期试着把工具文件塞进 `工具\` 子目录，结果游戏不认；实测**平铺在条目根目录**
> 时 `validationItems=0`，游戏照常接受。所以发行包 = 条目目录本身。

## 2. 伞形 + 卫星：为什么不是四个独立插件

最直觉的做法是四个功能各写一个 `d3d11.dll`。但这行不通，原因是一个硬约束：

> **同一个目标地址上只能存在一个 inline hook。**
> 四个独立 DLL 各自 `MH_CreateHook(NewInputManager.Update, ...)` 时，
> 后写入者的跳板存活，先写入者被静默覆盖 —— 表现为「装了新版旧功能就哑火」。

所以改成**伞形 + 卫星**：

```
                    ┌──────────────────────────────────────┐
   游戏进程          │  d3d11.dll  （伞形 hotkey）           │
                    │                                      │
   游戏每帧调用 ───► │  hook: NewInputManager.Update        │
   NewInputManager   │    ├─ 读物理键状态                    │
   .Update           │    ├─ 菜单门禁判定 → 派发点击         │
                    │    ├─ drive_satellites()  ←─ 每帧驱动 │
                    │    └─ 热重载配置文件                  │
                    │                                      │
                    │  LoadLibraryW("mod-speedkey.dll") ───┼─► sk_frame_tick()
                    │  LoadLibraryW("mod-pinattr.dll")  ───┼─► pa_frame_tick()
                    │  LoadLibraryW("mod-goldhand.dll") ───┼─► gh_frame_tick()
                    └──────────────────────────────────────┘
```

- **挂钩点唯一**：所有 inline hook 只由伞形安装。卫星一个钩子都不碰输入层。
- **卫星永不被卸载**：`LoadLibraryW` 计入引用计数，进程生命周期内不 `FreeLibrary`。
  卸载会撤走卫星已经装好的 MinHook 跳板 —— 等于自拆跳板，之后必有野指针。
- **跨 DLL 调用只走导出函数**：卫星用 `__declspec(dllexport)` 暴露
  `*_frame_tick` / `*_input_focus`，伞形用 `GetProcAddress` 拿指针存进 `g_sat_ticks[]`
  表里，每帧遍历调用。
- **一个卫星挂了不连坐**：装载失败、`GetProcAddress` 拿不到、它的指纹不匹配，
  都只影响它自己的功能；日志里会写清楚哪个指针是 `MISSING`。

`shared/exports.h` 定义这套接口，伞形与卫星共用同一份声明，避免签名漂移。

### 卫星的两种失效模式与对应闸门

| 闸门 | 全局开关 | 卫星自检 | 结果 |
|---|---|---|---|
| 游戏内 Mod 管理里勾选 | — | — | 未启用 → 全部功能停 |
| `[features] <卫星> = 0` | 伞形的 ini | — | 只用 ini 关掉某一个功能 |
| 卫星指纹/锚点不匹配 | — | 卫星自己的 | 只停该卫星 |

三层都通过才真正生效，任一层否决都是「静默停用 + 日志留痕」。

## 3. 挂钩点：为什么钩 Update 和 OnApplicationFocus

| 目标 | 为什么是它 |
|---|---|
| `NewInputManager$$Update` | Unity 主线程每帧都会跑。把它当**唯一的主循环入口**：读键、判门禁、驱动卫星、热重载都在这里做。 |
| `NewInputManager$$OnApplicationFocus` | 切出/切回游戏时拿到焦点事件，用来维护「只在游戏窗口在前台时响应热键」。 |

把一切都收束到这两个钩子上，带来两个好处：
**不需要额外线程**（除了一开始等 `GameAssembly.dll` 的加载线程），
**不需要跨线程同步**（所有游戏状态都在主线程访问）。这条约束贯穿整个代码库。

### 卫星的 tick 为什么也要从主线程出发

卫星不做自己的循环，只被伞形每帧调用一次。原因同上：Unity 的
`GameObject` / `Transform` / UI 状态都只能在主线程访问，从别的线程碰它们是未定义行为。
伞形的 `drive_satellites()` 在输入钩内部依次调用三个卫星的 tick，
天然满足「主线程、每帧一次」。

## 4. IL2CPP 调用约定上的坑

直接按 C 的直觉去调 IL2CPP 方法会踩一串坑，这里记录已经验证过的规则：

| 坑 | 规则 |
|---|---|
| **实例方法必须显式传 `this`** | IL2CPP 的实例方法是带隐式 `this` 的普通函数，签名里必须写出来。漏了 → 崩溃。 |
| **`async` / 迭代器方法直接调用不执行** | 这类方法只返回一个状态机对象，真正的工作在 `MoveNext()` 里。要手动推进状态机，或者改用非 async 的等价路径。 |
| **返回结构体走 sret** | 大结构体返回值由调用方传入隐藏的返回缓冲指针（`sret`），签名首参要补上。 |
| **布局不要猜** | IL2CPP 的字段偏移受托管类型布局影响，dump 出来的和运行时看到的不一定一致。凡是能用运行时自省的（IL2CPP 导出的 `il2cpp_field_get_offset` 之类），就不要写死偏移。 |
| **静态字段要用 `il2cpp_field_static_get_value`** | 静态字段不在实例里，取不到。 |
| **同名重载会在按名建表时互相覆盖** | 同一个名字有多个重载时，`name → RVA` 的字典只能留一个。必须反汇编、按参数个数挑出真正要的那个。 |
| **低地址是合法指针** | 元数据解析出来的类指针可能落在低地址，不能按「地址大小」判断有效性。 |
| **RVA 权威来源** | `arrayIndex = token.rid - 1`，`methodPointers[rid - 1]` 就是该方法 RVA（相对映像基址）。 |

`hotkey/src/menu.h` 里的 `resolved_class()` / `ready_class_slot()`
就是为「在不触发游戏业务静态构造的前提下拿到类指针」而写的。

## 5. 构建一致性：两道独立的检查

地址写对了，还要确认「**当前这个 `GameAssembly.dll` 就是我按它写地址的那一个**」。
项目里用两道互相独立的检查：

### 5.1 SHA256 白名单（`known_build()`）

对 DLL 旁边的 `GameAssembly.dll` 算 SHA256，比对白名单。**三态返回**：

| 返回值 | 含义 | 后续 |
|---|---|---|
| `1` | 命中白名单 —— 构建未变 | 走 `NATIVE` 重定位（恒等映射） |
| `0` | 哈希算出来了但不在白名单 —— 官方更新了 | 走 `ADAPTIVE` 重定位 |
| `-1` | 读不到 / 算不出哈希 —— 安装位置不对或环境异常 | **停机**（这是真的出问题了） |

关键点：**哈希不匹配本身不是错误**，它只决定走哪条重定位路径。
这两种路径都不会去调用未经校验的地址。

### 5.2 字节指纹（`fingerprints*.h`）

对每个我们要调用/挂钩的地址，记录它开头 16 字节（含通配位）。
启动时逐点 `memcmp`。

指纹的作用是「**地址自证**」：即使 RVA 数值没变，如果那里的机器码变了，
说明我们记错了、或者官方动了这个函数，此时停用比硬调更安全。

> 指纹只能证明「这里大概还是那个函数」，**不能**证明「我们理解的语义还是对的」。
> 它是一道廉价的早期止损，不是正确性证明。

### 5.3 为什么两道都要

- 只有 SHA256：官方更新后白名单不命中，什么都不知道，只能整体停。
- 只有指纹：`NATIVE` 构建下能自证，但换个构建后指纹也全变了，同样只能停。

两道合起来才有第 6 节说的「**构建已知 → 恒等；构建未知 → 重定位**」。

## 6. 运行时重定位层（`shared/rva_reloc.h`）

这是本项目的核心，也是「官方小更新不再需要跟版重发」的实现。

### 6.1 问题

源码里到处是 `FN(0x7FE260, ...)` 这种写死的 RVA。官方哪怕只是加了个无关功能、
把代码段整体挪了位置，这些地址全部指错 —— 而哈希白名单又不认识新构建，
结果就是**第一秒整体停机**。玩家看到的是「全部失效」，但官方其实什么都没针对我们做。

### 6.2 把 RVA 降级成「锚点」

改动只有一处咽喉点：

```c
/* 改造前 */
#define FN(rva, ret, ...) ((ret(*)(__VA_ARGS__))((BYTE *)ga + (rva)))
/* 改造后 */
#define FN(rva, ret, ...) ((ret(*)(__VA_ARGS__))((BYTE *)ga + rva_of(rva)))
```

`rva_of()` 把「我上次重解时的 RVA」翻译成当前版本的 RVA：

- `NATIVE` 模式：直接返回原值（恒等映射，零开销）
- `ADAPTIVE` 模式：查启动时算好的重定位表；没找回来的锚点返回 `0`
  （此时调用点必须已被闸门拦下，见 6.6）

因为所有模块的地址使用都收束在 `FN()` 宏 / `addhook()` / `MH_CreateHook()` /
少量 `rva_of(0x…)` 直连上，改造面从 171 处降到每个模块约 10 处。

### 6.3 掩码指纹怎么来

对每个锚点，从**上一次重解时的** `GameAssembly.dll` 采一段机器码，然后用
反汇编器（capstone）把「会随位置变化的字节」标成通配：

| 位置 | 处理 | 理由 |
|---|---|---|
| `jmp` / `call` 的 `rel8` / `rel32` 立即数 | **通配** | 是相对位移，代码挪位它就变 |
| RIP 相对寻址的 `disp32` | **通配** | 同上 |
| 指令 opcode / 寄存器编号 / 字面常量 | **保留**，逐字节必须相同 | 这些就是函数本身的特征 |

实测（2.2.0 → 2.2.4 跨四个版本）：**保留位上 56 / 57 个条目逐字节完全没变**。
这直接证明了「官方没改我们的函数，只是把代码挪了位置」，也是整套方案成立的实证基础。

### 6.4 为什么必须「唯一命中」

这是整套设计里最要紧的一条取舍，用血换来的：

> 实测 **16 字节**掩码指纹在 4 MB 窗口内有**上千个误命中**。
> 256 字节长指纹在 256 KB 窗口内才收敛到 93%。
> 「取最近的一个」在多命中时**没有判据** —— 一旦选错，就是拿着错误偏移
> 调用游戏函数，形态上正是历史上那次「启动闪退」。

所以判据定为：**窗口内恰好一个命中（`hits == 1`）才采用**，
`0` 个或 `≥2` 个一律判失败。命中数超过 64 直接早退（说明这是噪声模式，别白扫了）。

代价是会有一些点找不回来；收益是**永远不会拿错地址**。
配套的分级降级（6.6）保证「找不回来」只损失对应功能，不会连坐。

### 6.5 指纹长度自动升长

对每个锚点，依次尝试长度 **256 → 512 → 1024 字节**，取第一个能在窗口内唯一命中的。

实测中 256 字节时失败的 4 条，都是 Unity 的短 getter
（`Behaviour$$get_isActiveAndEnabled`、`Component$$get_gameObject`、
`GameObject$$get_activeInHierarchy`，以及 `Time$$get_frameCount`），
512 字节解决 3 条，**1024 字节全部收敛**。

最终四个模块 **81 个锚点全部唯一命中，零未收敛**。
报告样式：长度分布中 1024 字节的只有那 1 条。

### 6.6 分组与分级放行

锚点按功能归组，闸门也是分组的：

| 组 | 内容 | 失败后果 |
|---|---|---|
| `0` 核心 | 输入钩、游戏内 Mod 开关读取、帧计数 | 整个 Mod 停（没有这些跑不起来） |
| `1` | approach（自动接近，已废弃） | 只停 approach |
| `2` | wait 菜单热键 | 只停菜单热键 |

每个模块另有自己的模块级闸门：

| 模块 | 闸门 |
|---|---|
| hotkey | `wk_core_ok`（组 0）+ `wk_wait_ok`（全部锚点） |
| speedkey | `sk_reloc_ok` |
| pinattr | `pa_reloc_ok` |
| goldhand | `gh_reloc_ok` |

闸门在对应 `*_frame_tick()` 的首行检查，未通过直接 `return` ——
**绝不调用任何尚未解析的地址**。

### 6.7 三种模式

| 模式 | 何时 | 行为 |
|---|---|---|
| `NATIVE` | 哈希命中白名单 | 恒等映射；与没有这层时**逐字节相同** |
| `ADAPTIVE` | 哈希不认识 | 逐点扫描重定位 + 单点降级 |
| `SELFTEST` | `rva_mode=selftest` 手动开 | 即使构建没变也强制扫描，并把「查询锚点」人为偏移 `rva_shot` 字节 |

`SELFTEST` 是为了**可验证性**而存在的：它制造出「锚点全部过时」的等价条件，
从而可以在不换游戏版本的前提下，证明扫描器真的能从错误锚点恢复。
配合离线自测程序（把真实 `GameAssembly.dll` 以
`LOAD_LIBRARY_AS_IMAGE_RESOURCE` 映射进进程、不执行任何游戏代码），
跑的又是与出货 DLL **同一份** `rva_reloc.h`，所以结论可直接外推到线上。

配置项（伞形 `hslr-wait-hotkey.ini` 的 `[options]`，默认全部注释掉）：

```ini
rva_mode   = auto    ; auto / native / adaptive / selftest
rva_window = 0x40000 ; 搜索窗口半宽（字节）
rva_shot   = 0       ; 仅 selftest：人为偏移量
```

### 6.8 锚点表的生成与维护

`<模块>/src/rva_anchors.h` 是**生成物**，由内部工具从源码里扫出所有地址引用
（`FN(0x…)`、`addhook(0x…)`、`#define *_RVA 0x…`、`rva_of(0x…)`……），
再到当前构建的 `GameAssembly.dll` 上采样长掩码指纹，逐条尝试到唯一命中为止。

因为它是生成物，所以**跟着源码一起提交**（这样仓库能独立构建），
但有两条纪律：地址引用变了就要重新生成；重新生成必须对着同一个构建。

`fingerprints*.h` 与它分工不同：指纹表是「16 字节自证」，锚点表是
「长掩码 + 搜索窗口」，前者快而短，后者专为跨版本找回。

## 7. 与游戏 Mod 管理器的集成

游戏有一套自己的 Mod 管理：`MODS\<名字>\mod.json` 是条目清单，游戏把它汇总成
`mod_profile.json`，玩家在「Mod 管理 → Mod List」里勾选后点「套用變更」才落盘。

我们的做法：

- **条目根目录必须有 `mod.json`**，缺了游戏会直接忽略整个目录
  （日志写作「忽略無效 MOD 目錄」），Mod 列表随即变空。这是**唯一一条硬规则**。
- DLL 每帧读游戏写下的 `mod_profile.json`，只有「`modId` 匹配 且 记录为已启用
  且 游戏没标记它不兼容」三条同时满足才响应热键。
- `modId` 是匹配主键。工坊物品的主键形如 `<modId>@<文件ID>`，
  所以匹配时对 `@` 后缀做了容差，并在多个候选命中时取「或」。
- `force_enable = 1` 可忽略游戏内开关（**只用于本地排障**，正式订阅请保持 `0`）。

`installer.ps1` 对 `mod.json` 与封面图是**保留优先**：
条目里已有同 `modId` 的 `mod.json` 就原样不动（要 `-Force` 才重生成），
封面只补缺不覆盖 —— 免得把作者手写的名字/版本/说明和宽封面冲掉。

## 8. 交付形态上的几条纪律

- **三个 DLL 互相之间不导入**。所有共用代码（配置解析器、重定位层、代理骨架）
  都以「头文件 + `static`」的形式在每个 DLL 内各编译一份。
  这样任何一个卫星缺失或损坏，都不会让伞形加载失败。
- **零运行时依赖**：安装工具是 PowerShell 5.1（Windows 自带），
  DLL 只链 `advapi32` / `user32`（speedkey 另需 `gdi32`），不依赖 VC 运行库。
- **不使用注册表**。所有配置都在 ini 里，卸载 = 删文件，不留系统痕迹。
- **文件读写一律走长路径**（`\\?\` 前缀）。游戏装在深层目录或中文多层目录时，
  超过 `MAX_PATH` 会让 ini/日志静默打不开，从用户侧几乎查不出原因。
